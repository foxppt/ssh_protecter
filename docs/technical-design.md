# SSH 守门程序：首版技术设计草案

[简体中文](technical-design.md) | [English](technical-design.en.md)

日期：2026-11-02。目标平台：Rocky Linux 10。

本文记录已确认需求和建议实现方案，不代表程序已实现或已在目标系统验证。标注“建议”的细节尚未单独确认；依赖版本和内核行为需要通过目标环境验收。

## 1. 已确认的行为

| 项目 | 首版行为 |
| --- | --- |
| 形态 | Go CLI；前台运行服务，由 systemd 托管 |
| 用户 | 单用户，身份与授权数据结构预留多用户 |
| 初始化 | 首次通过终端绑定 TOTP，验证有效验证码后才启用 SSH 默认拒绝 |
| 网页身份验证 | 仅 TOTP，无密码；允许有效期内重复使用验证码 |
| 来源地址 | 直连使用网络连接对端；指定可信代理后才采用对应 IP Header |
| 授权目标 | 默认网页请求来源 IP，允许手动指定 IPv4 或 IPv6 |
| 临时授权 | 默认 5 分钟；再次验证从本次成功时间重新计时，不累加剩余时间 |
| 连接保留 | 到期只禁止新连接；有效期内断开全部连接也不提前撤销授权 |
| 永久白名单 | 配置中的 IP 集合，无需网页授权，仍需 SSH 自身认证 |
| 验证失败 | 同一来源 IP 滚动 1 小时失败 5 次，封禁验证入口 24 小时；均可配置 |
| 封禁与白名单 | 永久白名单不免除网页验证码失败限制 |
| 持久化 | IP、封禁/授权截止时间持久化，重启保留原截止时间 |
| 重载 | 类似 Nginx：先验证、再应用，失败保持旧的有效配置 |
| 网络范围 | IPv4、IPv6 保护和 SSH 端口均可配置 |
| Docker | 共存，只管理本程序的独立链和集合 |
| HTTPS | Go 加载证书直连；或 Nginx 终止 TLS 后转发 |
| 证书 | 外部工具申请、续期，文档说明部署流程 |
| 恢复 | 本地 root 可重新绑定，撤销临时授权，保留已有 SSH 连接 |
| 故障 | 不自动开放 SSH；已有临时授权按原定时间失效，永久白名单保留 |

## 2. 组件与职责

```text
浏览器 ── HTTPS ── [可选 Nginx] ── Go 授权服务
                                      │
                         持久化状态 ──┼── 独立防火墙表/链
                                      │
systemd ── 启动、重启、健康超时监护 ────┘

SSH 客户端 ── 内核防火墙授权检查 ── sshd 自身认证
```

- 单个 Go 二进制提供初始化、服务运行、配置检查、重载、状态查询和重绑定入口。
- 不自行 fork 到后台，不实现另一套长期运行的进程监控器。
- systemd 检测进程退出；Go 以受业务健康检查约束的心跳配合 systemd watchdog。
- 内核防火墙负责数据包判定和临时集合元素到期。服务退出不能删除基础防护规则。
- 建议使用 SQLite 存储状态，避免将不断变化的授权、封禁和验证失败记录混入人工配置文件。

## 3. 防火墙设计

### 3.1 独立对象

建议创建 `inet ssh_protecter` 表，包含：

- 一个挂在 `input` hook 的基础链，以及承载 SSH 判定的独立普通链。
- 受保护端口集合。
- IPv4 / IPv6 永久白名单集合。
- IPv4 / IPv6 带 timeout 的临时授权集合。

只替换自己的表内对象，不调用 `flush ruleset`，不修改 Docker 管理的表、NAT 或转发规则。hook 优先级需要结合目标机现有规则确定，不能仅靠链名假设执行顺序。

针对启用保护的地址族和受保护 TCP 端口，逻辑顺序为：

1. 保留符合连接跟踪状态的既有 SSH 连接。
2. 允许永久白名单来源。
3. 允许临时授权集合中的来源。
4. 拒绝其余连接。

其他端口不由本程序决定是否放行。关闭某个地址族保护表示本程序不限制该地址族，不表示禁用系统 IPv4/IPv6。

临时元素 timeout 使用 `原截止时间 - 当前时间`；恢复、巡检和配置重载都不能把它重置成完整 5 分钟。日常授权到期不依赖 Go 定时器删除规则。

### 3.2 Docker、firewalld 与作用范围

- 宿主机 SSH 走本机 `INPUT`；桥接容器端口通常经 DNAT 走转发路径，不纳入首版保护。
- host 网络容器与宿主机共享网络，其绑定受保护端口时同样受限制。
- 不以 Docker 的 `DOCKER-USER` 作为宿主机 SSH 守门入口，不要求切换 Docker 防火墙后端。
- nftables 中本链的 accept 不能覆盖其他基础链的 drop。firewalld 或其他防火墙仍需允许相应 SSH 端口，本程序在此基础上追加访问限制。
- 不为了加载本程序规则而额外启用可能清空全局规则的通用 nftables 服务。与 firewalld 的共存以其实际后端及 Rocky 10 验收结果为准。
- 需要记录并测试实际 Docker 版本、iptables/nftables 后端及 firewalld 状态，不能宣称兼容未经测试的所有组合。

### 3.3 保证范围

Go 崩溃、被终止或正常重启时，已经写入内核的默认拒绝规则保留，临时元素照常到期。表的生命周期不能配置为随创建进程退出而删除。

规则遭意外改动时，使用变更监测与定期核对恢复本程序对象。外部 root 执行全局清空规则会产生检测和恢复窗口；单机软件不能保证在过滤规则已被删除时仍零窗口阻断。首版不引入云安全组等第二层控制面。

## 4. 启动、初始化与监护

### 4.1 首次初始化

1. 通过终端以管理员权限启动初始化流程。
2. 生成 TOTP 密钥并展示绑定信息；密钥不得写入日志或命令行参数。
3. 输入有效验证码完成绑定，安全持久化配置和身份信息。
4. 校验防火墙计划与启动集成，再安装基础保护和 systemd 托管。

在绑定确认前，不改变 SSH 为默认拒绝。已有初始化信息时不重复绑定；后台无终端且未初始化时，应退出并提示通过控制台初始化，不能挂起等待输入。

### 4.2 基础保护与运行服务分离

建议使用同一二进制的两个执行入口，对应两个 unit：

- `ssh-protecter-guard.service`：一次性安装基础规则，成功后保持 active，不是另一个常驻进程。
- `ssh-protecter.service`：长期运行网页和授权服务，负责恢复与巡检。

为 sshd 添加对 guard 的 `Requires=` 与 `After=`；存在 socket activation 时同样覆盖对应 socket。仅写 `Before=sshd.service` 不足以保证 guard 一定被拉起或失败时阻止 sshd 启动。

guard 使用最后一次成功应用的保护配置，不依赖网页证书或 TOTP 服务就绪。这样证书或新配置损坏时仍可先建立基础拒绝；guard 无法安装规则时阻止 SSH 启动，通过控制台修复。

运行服务的日常重启不与 sshd 重启绑定；停止授权服务也不删除防护表。安装、启动、停止和卸载的副作用必须分别定义并验收。

### 4.3 健康与重启

- 建议 `Type=notify`，仅在基础规则、状态存储和监听器就绪后报告 READY。
- 使用 `Restart=`、重启间隔与启动频率策略处理退出；具体数值在目标机测试后设置。
- 心跳受有截止时间的状态存储检查、防火墙一致性检查和网页处理能力检查约束，不能由无条件计时器发送。
- 致命故障时停止新授权并退出或停止心跳；systemd 重启服务，不能通过放开 SSH 进行“自愈”。
- 磁盘满、数据库损坏、私钥不可读等故障记录清楚的原因，保持已有内核规则，交控制台处理。
- 保留 SELinux；按实际策略配置所需权限，不以关闭 SELinux 作为部署前提。

## 5. 状态、并发与恢复

建议的数据实体：

| 实体 | 主要字段 |
| --- | --- |
| 验证用户 | 稳定用户 ID、TOTP 密钥引用、启用状态 |
| 临时授权 | 规范化 IP、用户 ID、授权时间、UTC Unix 截止时间、状态/版本 |
| 验证失败 | 规范化请求来源 IP、失败发生时间 |
| 验证入口封禁 | 规范化请求来源 IP、UTC Unix 截止时间 |
| 配置代次 | 代次 ID、有效配置快照、应用状态 |

同一 IP 的续期、配置重载和规则修复必须由统一的状态协调逻辑串行化，防止后台巡检写回旧截止时间。IPv4-mapped IPv6 地址应规范化，避免同一个来源拥有两套计数。

按滚动窗口统计失败，不按整点清零。建议持久化窗口内失败事件；验证成功不清零尚在窗口内的失败记录。已封禁请求不继续延长封禁时间，重复请求不能把固定 24 小时变成无限封禁。

SQLite 事务和内核规则提交不是一个共同事务，不能声称二者原子提交。建议采用可恢复的操作记录：

1. 校验并生成授权计划，持久化待应用操作及明确的截止时间。
2. 原子提交本程序所需的内核集合变更。
3. 完成持久化状态后才返回授权成功。
4. 在中间步骤崩溃时，重启通过操作状态恢复；无法确定状态时暂停新授权，避免擅自扩大权限。

失败或超时的网页提交可能已有副作用，重试处理应明确返回当前截止时间。恢复流程必须测试各持久化/内核提交边界，不能只测试正常重启。

机器重启后不可能保留原 TCP/SSH 会话；“已有连接保留”针对授权到期和守门程序操作，不能解释为机器重启后连接仍存在。

## 6. 配置与重载

建议配置结构如下，仅用于展示字段设计，尚非已实现格式：

```yaml
ssh:
  ports: [22]
  protect_ipv4: true
  protect_ipv6: true
  permanent_allow_ips: []

authorization:
  duration: 5m

verification:
  failure_window: 1h
  max_failures: 5
  ban_duration: 24h

http:
  mode: direct_tls
  listen: ":443"
  tls_cert_file: /etc/ssh-protecter/tls/fullchain.pem
  tls_key_file: /etc/ssh-protecter/tls/privkey.pem
  trusted_proxies: []

storage:
  path: /var/lib/ssh-protecter/state.db
```

- IP 使用严格地址解析，首版永久白名单建议只接受单个 IPv4/IPv6 地址，不隐式扩展网段。
- 配置未知字段、重复字段、空端口集、重复/非法端口、不合法时长及证书与监听方式冲突应报错。
- 建议配置限 root 写，运行状态目录限服务身份访问；密钥不得出现在状态输出中。
- 配置检查需区分纯解析检查与需要目标系统权限的完整环境检查。
- 重载入口先读取和检查新配置，生成规则计划并执行内核校验，准备证书等资源，然后应用；不能校验前停止现有监听器。
- 本程序的内核规则变更使用事务批次，避免先删表后添加造成中间空窗。只允许一个重载任务运行。
- 配置文件、运行快照、数据库与内核跨资源一致性通过配置代次及恢复记录实现，不假定一个文件重命名可以提交全部资源。
- 应用前失败保留旧状态；跨资源应用中途失败尝试恢复旧代次，无法确认恢复成功则停止新授权并保留尽可能严格的基础规则，明确报告故障。

建议策略：调整放行/封禁时长仅影响后续事件，已有记录保留原截止时间；永久白名单更新在重载成功后生效。监听地址、模式及存储路径的变更首版可要求重启，检查阶段明确拒绝作为热重载应用，不静默忽略。

变更受保护端口/地址族会改变安全范围；从配置删除端口表示本程序不再限制该端口。程序不能自动修改 sshd 配置，也不能声称配置某个端口就证明 sshd 正监听该端口。

## 7. HTTPS 与来源地址

- 直连：Go 终止 TLS，使用网络连接对端作为来源 IP，忽略客户端自填来源 Header。
- Nginx：建议 Go 只监听回环地址，Nginx 负责 TLS；代理覆盖来源 Header，不透传浏览器自填值。
- 仅在连接对端属于可信代理范围时读取来源 Header；多层代理必须明确地址链解析规则，不能无条件取最左边地址。
- 用户填写的待放行地址与来源地址分开保存；所有失败限制都针对来源地址，不允许填写另一个 IP 转移封禁。
- 验证成功后不要建立一个长期免 TOTP 的网页登录会话。每次申请/续期仍提交验证码，展示实际授权 IP 与截止时间。
- 验证使用 POST，请求体长度受限，日志不含验证码；网页交互需检查同源请求，避免跨站代提交。
- 证书文件被外部工具更新后，通过经过校验的重载重新加载。Nginx 模式由外部工具触发 Nginx reload。

部署资料现见 `docs/deployment.md`、`docs/reload.md` 与 `deploy/nginx/ssh-protecter.conf`，包含 TLS、回环上游、来源 Header 覆盖、请求限制、续期重载与系统配置说明；SELinux、firewalld 和代理绕过行为仍需目标机验收。

## 8. 时间、凭据恢复与限制

TOTP 与持久化截止时间都依赖正确的系统时间。建议部署要求可靠的系统时间同步；发现明显回拨或时钟不可信时暂停新授权并报告原因，不重新赠送授权时间。具体异常阈值及重启后时钟可信判定需要专项设计和故障测试。

允许验证码在有效窗口内重复使用是已确认需求，不加入成功时间步去重。验证码接受窗口建议采用常见 30 秒周期并给有限时钟偏差容忍；不能因校验失败自动扩大窗口。

重绑定命令仅本地 root 可用，先验证新绑定，然后协调撤销全部临时授权并切换密钥；旧密钥立即失效，永久白名单保留，已有 SSH 连接不主动断开。不得通过网页提供无验证重绑定入口。

按公网 IP 授权不能区分同一 NAT 出口的不同设备。SSH 仍需独立身份认证；本系统不替代 SSH 密钥或账号管理。

## 9. 验收计划

必须在可使用控制台恢复的 Rocky Linux 10 虚拟机中验证，Windows 开发目录无法证明 Linux 防火墙行为。

1. IPv4/IPv6 默认拒绝、手动目标地址、多端口及永久白名单。
2. 临时放行到期拒绝新连接、保留已有会话；全部断开不提前失效。
3. 并发续期与巡检不会缩短/重复延长截止时间，重新授权从本次成功计算。
4. 滚动失败窗口、阈值触发封禁、重启后失败记录与封禁继续生效。
5. 守门程序崩溃、卡死、正常重启期间基础规则保留，临时授权正常到期。
6. 整机重启：基础保护先于 SSH 生效，仅恢复未到期授权的剩余时间。
7. 证书或新配置损坏：旧配置重载不受影响；启动时基础规则仍生效。
8. 数据持久化和内核应用每个中断点的恢复、磁盘满、数据库只读/损坏。
9. Docker 容器出网、端口映射、Docker 重启及 firewalld reload/restart。
10. 伪造 Header、未信任代理、直连上游、IPv4-mapped IPv6 地址与跨站提交。
11. 配置非法、规则应用失败、进程在重载中被终止：旧配置或保守恢复状态可解释且可查询。
12. 重绑定撤销临时授权，永久白名单与既有 SSH 会话保留。
13. 规则意外删除后恢复，以及系统时钟跳变时的实际行为和边界。

建议按“CLI/配置与状态存储 → 内核规则与系统启动集成 → TOTP 与网页 → HTTPS/Nginx → 故障验收”推进实现。
